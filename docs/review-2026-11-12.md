# Rune — Deep Review and Resume Plan

**Reviewed commit:** `5d940ae` — *feat(array): 6e-mutators push/pop/shift/unshift dispatch + length strictness + key-model* (2026-09-13)
**Review date:** 2026-11-12
**Codebase:** 75,323 lines of Rust across 16 workspace crates; 874 prebuilt unit/integration tests; local test262 checkout.
**Reviewer stance:** preserve the novel architecture; do not add features on top of defects that make ordinary programs wrong.

---

## 1. Executive verdict

Rune is a real engine, not a toy: it has a genuine stack VM, a NaN-boxed value representation, immutable content-addressed shapes, SIMD-shape dispatch, a moving semi-space GC, generators, classes, ESM, a baseline/trace JIT, and an AOT-first persistent-cache story. The design is worth preserving.

It is **not yet a safe base for feature work**. Four independent defects break ordinary JavaScript under conditions the current test suite rarely creates:

1. **Self-moving object/array growth breaks aliases** — adding the 9th property to `{x:42}` stored in an array makes the array's element unreadable. This is deterministic, needs no GC, and is a direct consequence of the inline-slot layout plus `grow`.
2. **The GC root set is incomplete** — `this`, constructor objects, function pointers, private-name tables, generator receivers/environments, and the microtask queue are not roots. A normal method call plus ~3M allocations returns `undefined`, corrupts private-field access, drops promise callbacks, or panics with a stale pointer.
3. **Pending state machines are single-flight `Option`s** — a `map` inside a `map` callback truncates the outer result; `forEach` nesting silently visits one outer element; nested `filter`/`map` throw. This is not a corner case: nested array callbacks are everyday code.
4. **The JIT silently miscompiles common loops** — a float accumulator loop over 1,000 iterations returns the value after 52 iterations; branchy Smi loops return wrong sums; no bailout is reported. JIT is on by default and has no runtime off switch.

The green suite (874/874) is real but measures the happy path. Current test262 is **10,656 passed / 53,658 total (27% of executed)**. A differential sample of 55 everyday programs matched Node 22 on 44; the meaningful mismatches include object-growth aliases, nested array callbacks, captured-variable update expressions, arrow lexical `this`, function hoisting, top-level TDZ, `finally` after `return`, and `Math.round(-0.5)`. Separate probes found that async continuations never resume and ESM live bindings do not update.

**Recommendation:** freeze the v1.0 feature checklist and run a 2–3 week soundness sprint. The architecture is salvageable; the fixes are tractable if ordered correctly. Make the JIT opt-in immediately. Fix memory safety and continuations before conformance and performance.

## 3. What is genuinely good (preserve this)

1. **Value representation.** NaN-boxed `Value` with float self-tagging (arXiv 2411.16544) is compact and elegant. Smis, heap pointers, sentinels, and raw `f64`s share one `u64`; float arithmetic is allocation-free. Keep it.
2. **Immutable, content-addressed shapes.** Hash-consed shapes with attribute bytes make ICs sound across attribute changes and are the right foundation for persistent caches. The basic design is good; the unbounded global table is the problem, not the idea.
3. **SIDT (shape-indexed dispatch).** The O(1) polymorphic IC idea (N=16, SIMD compare) is a defensible differentiator. It needs correctness tests under GC and growth, not a redesign.
4. **AFPC concept.** AOT-first persistent compilation is the product wedge. The cache format and native-code installation exist and work for the happy path. It needs source identity and invalidation, not abandonment.
5. **A real interpreter.** Frames, lexical environments, try/finally, generators, private fields, modules, and a broad builtin surface. The interpreter should be treated as the semantic reference for the JIT.
6. **The pending-machine CPS pattern.** Suspending a builtin when a JS callback must run and resuming in the `Return` handler is the right instinct for async/await and callback-taking builtins. The bug is the container (`Option`, one per machine) and the global depth rebase, not the concept. A continuation stack preserves the design.
7. **Engineering hygiene.** `cargo fmt` clean, 874 tests, extensive progress logs, explicit invariants in comments, and a history of root-causing hard bugs (GC duplicate roots, JIT zombies, let-for semantics). This is a team that can execute a soundness sprint.

## 4. P0 findings

### F1. Self-moving growth breaks aliases and the copying GC's forwarding contract

**Severity:** P0 — deterministic wrong answers, use-after-free, UB.

**Repro A (object, no GC, 20 lines of JS):**

```js
var o = { x: 42 };
var a = [o];
for (var i = 0; i < 20; i++) { o["p" + i] = i; }
print(a[0].x);           // Rune: undefined; expected 42
```

The threshold is exact: adding `p0..p7` is fine; adding `p8` (the 9th property) grows the object and `a[0]` becomes unreadable. `Object.keys(o)` still sees the new properties; the array element points at the old, forwarded copy.

**Repro B (array, no GC):**

```js
var a = [1];
var ar = [a];
for (var i = 0; i < 20; i++) { a.push(i); }
print(ar[0].length);     // Rune: 4; expected 21
```

**Why it happens:**

- `crates/rune_core/src/object.rs` (`JSObject::grow`) and `crates/rune_core/src/array.rs` (`RuneArray::grow`) allocate a replacement in the **active semispace**, copy the header/slots, and mark the old header `TAG_FORWARDED` (single hop).
- `Vm::update_heap_reference` (`vm.rs:11664`) rewrites only the operand stack, active-frame locals/`this`/`constructed_object`/`env` slots, globals, `jit_locals_buffer`, and `last_locals`. It does **not** scan array elements, object slots, suspended generators, pending-machine fields, microtask queues, module environments, or try-frame stashes.
- Heap reads do not resolve `TAG_FORWARDED`; a stale `Value` is passed to `load_property_recursive`, which sees an unknown tag and returns `undefined` (or dereferences a recycled header, as the panic below shows).

**The GC interaction is worse.** `SemiSpace::forward_object` (`gc.rs`) does:

```rust
if (*obj).is_forwarded() { return (*obj).forwarding_addr(); }
```

A grow copy lives in the **same from-space semispace**. On the next collection, a root/container slot pointing at the old object is forwarded to the grow copy in from-space and returned without being copied to to-space. The object is not relocated, and after the flip it can be overwritten. This is a use-after-free window even for roots that `update_heap_reference` did rewrite.

**Evidence of hard failure:** a `.call({v:99})` method that allocates 3M objects panics with `shape pointer is null for object at 0x…`; a queued promise callback panics with `misaligned pointer dereference: address … 0x1` in `push_callback_call` (`vm.rs:3625`).

**Options:**

- **Target (recommended): stable headers, separate backing stores.** Keep the object/array header at a stable address; store property slots/elements in a separate buffer (or fixed-size chunks) referenced by the header. Growth reallocates the buffer and updates the header pointer; aliases to the header remain valid, and the semi-space GC only moves headers. This eliminates the class permanently, at the cost of one indirection on element/property access and a change to layout-aware GC/JIT code.
- **Interim: forwarding-aware access + complete roots + chain canonicalization.** Resolve forwarding in `Value::heap_ptr` (a header load/branch per heap access), add an explicit resolver for raw pointers, make `forward_object` follow chains and copy a final from-space target, and complete the root set (F2). This preserves inline slots and is much less invasive; the risk is missing a raw-pointer path and the per-access cost. It is a good way to get correctness back quickly, but should not be the v1.0 end state.

The important decision is to **stop growing inline objects as they do now**. Every week of new features adds more code that assumes the stale-pointer behavior is harmless.

**Acceptance tests to add first:** the two repros above, plus a variant with a GC triggered after grow, plus aliases in object slots, generators, pending machines, and microtasks. These should fail before the fix.

### F2. The GC root set is incomplete

**Severity:** P0 — wrong values, panics, use-after-free for ordinary code.

`Vm::register_roots` (`vm.rs:3324`) is a manually maintained list. It roots the operand stack, frame `locals`/`lexical_slots`/`env`, try-frame saved exceptions, `last_locals`, generator `locals`/`lexical_slots`/`stack`, builtin prototypes/constructors/wrappers, keys, string cache, globals, module environments, the JIT locals buffer, the pending exception, and the pending machines. It does **not** root:

- `Frame.this` and `Frame.constructed_object` — the receiver and the `new` object exist only in the frame during a call.
- `Frame.func_ptr` — a heap `Func` pointer, the only reference while the function executes.
- `Frame.private_name_ids` — a heap `RuneArray` used by private-field opcodes.
- `Generator.this`, `Generator.env`, `Generator.try_frames[*].saved_exception`, and `Generator.abrupt` — a suspended generator's receiver/environment and pending abrupt completion.
- `Microtask.callback`, `Microtask.args`, and the `PendingPromiseCtor` values inside queued microtasks.
- `AsyncTask.promise` — the outer promise of an async function.
- `promise_reactions` is unused (dead field), so the promise-object reactions array is the real storage; it is traced, but only after its callback Values survive the queue.

**Confirmed behavior (all with `--jit-stats` showing 0 JIT entries where relevant, so this is GC, not codegen):**

```js
// this lost
var o = { v: 7, m: function () {
  for (var i = 0; i < 3000000; i++) { var t = { n: i, s: "z" + i }; }
  return this.v;
}};
print(o.m());            // undefined (expected 7)

// constructor object lost
function C() {
  for (var i = 0; i < 3000000; i++) { var t = { n: i, s: "z" + i }; }
  this.v = 42;
}
var c = new C();
print(c.v);              // undefined (expected 42)

// private name table lost
class C2 { #x = 41; m() {
  for (var i = 0; i < 3000000; i++) { var t = { n: i, s: "z" + i }; }
  return this.#x + 1;
}}
print(new C2().m());     // TypeError: Private field access outside class body

// generator receiver lost
var o2 = { v: 99, g: function* () {
  yield 1;
  for (var i = 0; i < 3000000; i++) { var t = { n: i, s: "z" + i }; }
  return this.v;
}};
var it = o2.g();
print(it.next().value);  // 1
print(it.next().value);  // undefined (expected 99)

// queued promise callback lost / crashes
Promise.resolve(7).then(function (v) { print("cb", v + 1); });
for (var i = 0; i < 3000000; i++) { var s = "z" + i; }
print("sync");           // prints sync; "cb" never runs; often panics
```

The `push_callback_call` panic is the worst case: a stale callback Value decodes to a non-aligned "pointer" (e.g. `0x1`) and dereferencing it aborts the process. This is not merely a wrong-value bug.

**Root cause:** manual root lists and duplicated reference-update logic are not enforceable. The GC has a `RootProvider` trait, but the provider omits half the frame/generator/microtask state. `update_heap_reference` has the same omission in a different form.

**Fix:**

1. Add every missing root above. Prefer a single exhaustive visitor/macro over parallel hand-written lists.
2. Add a `gc_stress` mode: a tiny semispace plus a counter that collects every N allocations (or every allocation), and run the whole integration suite and a semantic corpus under it. The current `Context::new_small()` (1 MiB) is not enough because the tests never allocate enough to collect while a call is live.
3. Add regression tests for each bullet above.
4. Consider making `Value::heap_ptr` resolve forwarding (F1) so roots that are missed in a container are at least self-healing until the next collection.

### F3. Pending machines are single-flight `Option`s; nested callbacks corrupt or truncate

**Severity:** P0 — silent wrong answers and TypeErrors in everyday code.

The VM keeps one `Option<ArrayOpState>`, one `Option<PendingSortOp>`, one `Option<PendingFromOp>`, etc. Builtins do:

```rust
vm.pending_array_op = Some(op);
```

unconditionally. The `Return` handler `take()`s the single state, checks `frames.len() == source_frame_depth`, and drops the continuation if the depth does not match. `rebase_pending_depths` mutates **every** pending machine's depth whenever any callback frame is pushed.

**Repros:**

```js
[1,2].map(function (x) {
  return [10,20].map(function (y) { return x + y; });
});
// Rune: [11,21] (outer map truncated / inner arrays lost)
// Node: [[11,21],[12,22]]

var s = 0;
[1,2].forEach(function (x) {
  [10,20].forEach(function (y) { s += y; });
  s += x;
});
print(s);               // Rune: 31; expected 63

[1,2].filter(function (x) {
  return [10,20].map(function (y) { return y; }).length === 2;
});
// TypeError: undefined is not a function
```

A getter that calls `map` while an outer `map` callback is live (`o.v` pattern) also fails. Sort comparators calling `sort`, `Array.from` inside a mapper, and Promise callbacks nested in array callbacks are all in the same class.

**Why it matters:** this is not a spec edge case. `arr.map(x => x.items.map(...))` is one of the most common JavaScript shapes. A `forEach` that silently stops after the first outer element is a data-corruption bug, not a missing feature.

**Fix:** replace each `Option<MachineState>` with a continuation stack. Two viable shapes:

- One `Vec<Continuation>` where `Continuation` is an enum over all machine states; a JS frame owns/resumes the innermost continuation; completion pops to the outer continuation.
- Per-machine `Vec<State>` stacks with a stable `frame_depth` per entry and a callee-identity guard; on completion, pop and let the outer callback's return resume the outer state.

Either way:

- Remove `rebase_pending_depths`; a continuation's frame depth must not change because an unrelated callback was pushed.
- Resume only the continuation whose awaited frame is the one returning; use callee identity + depth, not depth alone.
- Migrate the array machine first (map/filter/forEach/reduce/search), add the nested tests, then sort/from/length/species/copy, then Promise/async. Keep the old machine API as a thin wrapper until each is migrated.
- Add a debug assertion that a second suspension of the same machine pushes rather than overwrites.

### F4. The JIT silently miscompiles common loops and cannot be turned off

**Severity:** P0 — silent wrong results; the JIT is on by default.

**Repros (debug binary at HEAD; `--jit-stats` in parentheses):**

```js
function f() {
  var s = 0.5;
  for (var i = 0; i < 1000; i++) { s += 1.25; }
  return s;
}
print(f());
// Rune: 65.5 (value after 52 iterations), expected 1250.5
// JIT stats: 1 entry, 0 bailouts
```

```js
function grow(n) {
  var acc = 1;
  for (var i = 0; i < n; i++) { acc = acc * 1.5; }
  return acc;
}
print(grow(100));       // Rune: 0; expected 4.06e17
print(grow(200000));    // Rune: 0 (single cold call)
// But: warm the loop with 100 calls to grow(50), then grow(200000) -> Infinity (correct)
```

That last line is the key diagnostic: the trace is correct when it is recorded during a short warm-up call and entered later from the loop header, but wrong when it is compiled mid-call and entered at the current iteration. The result is state-dependent, so a single "it worked in the benchmark" is not evidence.

More cases:

```js
function f(n) { var s=0; for (var i=0;i<n;i++){ if (i%2===0) s+=i; else s-=1; } return s; }
f(100);                 // Rune: 1458; expected 2400

var s = ""; for (var i=0;i<20000;i++){ s = s + "x"; } print(s.length);
// Rune: 20378; expected 20000
```

The 52-iteration cutoff is exactly the documented "50 iterations + 2 during compile" window (see `progress.md`). The native trace executes one iteration (or zero) and exits the loop instead of continuing; no bailout is recorded, so the interpreter never gets a chance to correct it. `--no-inline` and `--stencil-jit` do not change the result.

**Why this is a P0:** the JIT is not an experimental side path. `rune_interpreter` defaults to `jit`, `rune_embed` depends on it with default features, and the CLI has no `--no-jit`. A user running a 1,000-iteration loop gets a wrong answer with no warning. The interpreter is the correct reference; the optimization must never be able to silently diverge.

**Immediate action (cheap, high value):** make the JIT opt-in. Either set `default = []` for `rune_interpreter`, or add a runtime `jit_enabled` flag with `--jit` (default off), and make `rune_embed` propagate a no-JIT feature. Ship the interpreter-correct engine until the trace contract is understood.

**Then:** add a differential JIT harness: run every semantic corpus program with JIT on and off and require identical observable output, including side-effect logs. Instrument the trace entry/exit with iteration counts and per-iteration state comparison in debug builds. The likely root cause is a mismatch between the interpreter state at the back-edge and the trace's assumed entry state (locals/JIT-stack depth), not the arithmetic helpers; the 52/53 boundary and the warm-vs-cold difference point at trace entry, not at `Add`/`Mul`.

**Also:** x86-64 `codegen.rs` is described as updated "textually only" and dead; the README architecture table still says "AArch64 + x86-64". Decide and document one story.

### F5. Async/await continuations never resume; `Promise.all` never settles

**Severity:** P0 for the async feature, but independent of the memory-model fixes.

```js
async function f() {
  print("before");
  await 1;
  print("after");
  return 9;
}
f().then(function (v) { print("resolved", v); });
print("sync");
```

Rune prints `before` and `sync`; `after` and `resolved` never appear. `async function f(){ return 5; }` without `await` works and resolves. `Promise.all([Promise.resolve(1), Promise.resolve(2)]).then(...)` never runs its callback. `async () => {}` is a parse error.

This is not a small gap: `await` is the feature. The existing tests explain the miss:

```rust
// integration_test.rs:7549
async function f() { result = 10; await 1; result = 20; }
var p = f();
result;        // asserts 10 — only the synchronous prefix
```

`test_async_await_chaining` asserts `results.length == 1` — i.e. it asserts that the continuation has **not** run. The tests validate the suspension point, not the resumption. That is a test-design bug, not a subtle conformance miss.

**Next step:** trace one `await` end-to-end: the `Await` opcode calls `Promise.resolve(val)` and `.then(async_continue_bridge, async_reject_bridge)`; the bridge must be invoked from a microtask, set `pending_async_gen`, and the `Return` handler must restore the generator frame. Determine whether the bridge is never called, the pending state is consumed by the wrong `Return`, or the microtask queue is drained before the bridge's promise reaction is registered. Add end-to-end tests (`print` after await, `.then` value, rejection, multiple awaits, await in a loop, async arrow) and keep them in the non-JIT and GC-stress suites.

## 5. P1 findings

### F6. ESM live bindings are not live

`dep.mjs`:

```js
export let count = 1;
export function inc() { count++; }
export default 42;
```

`main.mjs` imports `count`/`inc`, prints `1`, calls `inc()`, prints again. Rune prints `1, 1`; Node prints `1, 2`. The README claims live bindings and the module tests do not mutate an imported binding after import. Fix the module-record binding path and add a mutation test (and a namespace-object mutation test).

### F7. Core semantics gaps that block ordinary code

These are not all in the current known-gap list. Some may be B8 items, but they are visible in simple programs:

- **`finally` after `return` is skipped.**
  ```js
  function f(){ try { print("try"); return 1; } finally { print("fin"); } }
  print("res", f());   // Rune: try, res 1 (no fin); Node: try, fin, res 1
  ```
  The throw path works (`try`, `fin`, `caught`), so the completion handler is only wrong for `Return`.
- **Function declarations are not hoisted.**
  ```js
  print(typeof f); f(); function f(){}
  // Rune: "undefined", then TypeError; Node: "function", then call
  ```
  Mutual recursion between top-level declarations works only because both declarations execute before the call. This is a common script shape and a known B8 item; it still disqualifies many real scripts.
- **Arrow functions do not capture lexical `this`.**
  ```js
  var o = { v: 7, m: function () { return (() => this.v)(); } };
  print(o.m());          // Rune: TypeError (this undefined); Node: 7
  var f = () => typeof this; print(f());  // Rune: undefined; Node: object
  ```
- **Update expressions on captured variables corrupt the VM stack.**
  ```js
  function mk(){ var n=0; return function(){ return ++n; }; }
  print(mk()());         // Rune (debug): panic "Return: stack underflow (len=2, base=2)"
  ```
  `++n; return n;` as a statement works, as does `n = n + 1`. The value-producing update in an expression context is the broken case; it is likely an emitter stack-balance bug, and release builds would corrupt rather than panic.
- **Top-level script TDZ is not enforced.** `try { print(x); } catch(e) { print(e.name); } let x = 1;` prints `undefined` instead of throwing `ReferenceError`. Function/block scope TDZ works.
- **Minor:** `Math.round(-0.5)` returns `+0` instead of `-0`.
- **CLI:** an uncaught exception prints `Error: Uncaught: …` but exits with status 0 (`main.rs`). Scripts cannot rely on exit codes. The test262 runner has a separate `test262-exec` path that maps outcomes correctly, so this does not invalidate the conformance runner, but it does affect users.

### F8. AFPC cache executes stale code

```sh
echo 'print("first", 111);' > prog.js
rune --cache=c.cache prog.js      # first 111
echo 'print("second", 222);' > prog.js
rune --cache=c.cache prog.js      # prints first 111 — the edit is ignored
```

`load_afpc_cache` loads bytecode/shapes/ICs/native code and `eval_bytecode_owned` executes it without checking the current source. There is no source hash, path key, compiler version, or resolver-input hash in the header; `AFPC_VERSION` is 5 in code while the README says 2. `--cache` is also bypassed entirely for `-e` (the inline path executes before the cache branch). For a product whose pitch is "compile once, cache forever", this is a correctness and deployment-safety issue: a stale cache silently runs old code.

Fix: hash the source (and module resolver outputs) into the cache header, verify on load, fall back to compilation on mismatch, include engine/bytecode-format version, and document that the cache is content-addressed by program. Consider a `--cache` UX that reports hit/miss and invalidates loudly.

### F9. Global shape interning leaks without bound

Shapes are `Box::leak`ed into a process-global `Mutex<HashMap<…>>` and never evicted (`rune_core/src/shape.rs`). Measurements:

| Distinct property names | Max RSS |
|---|---|
| 10,000 | 42.8 MB |
| 100,000 | 83.6 MB |
| 300,000 | 189.7 MB |
| baseline | 37.7 MB |

At ~500 bytes per shape, a long-running edge worker that sees user-controlled property names grows forever. Shapes are also shared across contexts, so one context's garbage retains memory for all. The content-addressed design is good for AFPC; it needs a bounded/arena strategy (per-context tables, refcounts, or an LRU that keeps shapes referenced by live objects and persisted caches). At minimum, document a cap and provide a way to reset between requests; ideally make shape storage per-context with stable IDs for persisted caches.

### F10. Tests, CI, and docs overstate readiness

- The 874 tests are green, but the suite lacks: nested reentrancy, GC stress, async continuation, ESM mutation/live bindings, hoisting, arrow `this`, `finally`+`return`, captured updates, grow aliases, and differential comparison.
- The full test262 run is 27%; `conformance-report.md` is stale (19%, Aug 22, excluded intl402) and not regenerated.
- `cargo test --workspace` requires the git-only `mmtk` dependency of `spike_mmtk`; offline builds fail before compiling any product crate. Move spikes to a separate workspace or behind an optional feature; add `rust-version` (edition 2024 requires 1.85; README badge says 1.83).
- CI's `--no-default-features` job only builds `rune_interpreter`; `rune_embed`/CLI always pull the JIT, so there is no product no-JIT build.
- `target/release/rune` is stale (Sep 4); benchmarks/cold-start numbers should be regenerated at HEAD with a fresh release build.
- `rune_debugger` (9 lines), `rune_capi` (60 lines), and `rune_builtins` (24 lines) are placeholders; the docs present them as crates in the architecture. Either implement or label as stubs.

## 6. Lesser findings / design risks

1. **Hardcoded layouts in the GC.** `gc.rs` parses object, array, func, env, promise, regexp, map, set, date, typed-array, and string-object offsets by hand. One layout change silently corrupts the heap. Add `const` offset assertions (`offset_of!`) or a `Trace` trait/descriptor generated from one source. This is a cheap, high-leverage robustness improvement.
2. **`update_heap_reference` duplicates root knowledge.** Even after F1/F2, it scans a subset in a different order from `register_roots`. Replace both with one root visitor; a move should only need one list.
3. **Single-hop forwarding.** `forward_object` returns a forwarded target without checking its space or following chains. Grow creates exactly the case it cannot handle. Fix this even if grow is removed, because the GC should be invariant-safe.
4. **Shape IDs are `fxhash64`.** Two different property-name sets can collide in 64 bits; the interning table key prevents shape-table collisions but the **id** used by ICs/AFPC is just the hash. Add a debug collision check or use a 128-bit id for persisted code.
5. **Unsafe density.** ~1,960 `unsafe` occurrences in 75K lines, raw pointers in `Vm` fields, manual root registration, and manual `Vec` pointer stability. This is inherent to the design but needs guardrails: Miri/ASan where possible, a `debug_assert`-rich stress build, and a policy that raw pointers never outlive a callback without a root.
6. **`push_root` dedup is O(n).** Roots are ~400, so it is acceptable, but a dedup hash set or a scope-local root guard would be clearer and less error-prone.
7. **Promise side table is dead.** `promise_reactions` is declared and initialized but never used; remove it or document why. Dead fields in a GC-adjacent structure invite future mistakes.
8. **Root duplication.** `pending_length_op.stash_this` is pushed twice; harmless due to `push_root` dedup, but a sign that the list is hand-maintained.

**Gate:** no wrong values or panics under GC stress; nested-container aliases survive growth; promise callbacks survive a forced GC; methods/constructors/generators keep `this`.

**Gate:** nested callbacks produce the same results as Node; async functions settle and run their continuations; ESM live bindings update.

2. Build a JIT differential runner (same program, on/off) over the corpus and test262 subsets.

4. Re-enable JIT only when JIT-on and JIT-off observably agree across the corpus, with bailouts allowed but never silent divergence.

## 8. What not to do

- **Do not add more array methods or spec-conformance slices on top of F1/F2/F3/F4.** Each new machine inherits the single-flight and root-registration hazards.
- **Do not trust the green suite as a semantic gate.** It is a regression net, not an acceptance suite; the async tests assert the suspension, not the resumption.
- **Do not rewrite the interpreter or the value representation.** They are the best parts of the codebase. The fixes are localized to growth, roots, continuation storage, and the JIT gate.
- **Do not keep the JIT default-on while debugging.** A silent wrong answer is worse than a slower correct answer; the cold-start wedge does not depend on hot-loop JIT.
- **Do not let the AFPC cache run unverified source.** A stale cache is indistinguishable from a compiler bug in production.

## 10. Open questions for the maintainer

1. **Semantics vs conformance priority.** Is the goal "run real serverless workloads correctly" or "raise test262"? They imply different next steps; this review recommends real-workload correctness first.
2. **Layout appetite.** Are you willing to change object/array layout to stable headers + separate slots? That is the durable fix for F1; the forwarding interim is smaller but leaves a per-access cost and a class of missed paths.
3. **Is JIT required for v1.0?** If not, ship interpreter-only and treat the JIT as a separate research track. The cold-start wedge is already real.
4. **AFPC trust model.** Is the cache keyed by an external deployment hash (then document it), or must the engine self-verify source (then implement the hash)? The current behavior is unsafe either way unless documented.
5. **Memory ceiling for the edge story.** 36 MB baseline and ~500 B per unique shape are not "minimal memory". What is the target (RSS per isolate, max shapes, max heap)?
6. **What is the acceptance workload?** Pick 3–5 real programs (HTTP handler, JSON transform, data pipeline, module graph) and make them pass under GC stress and JIT-on/off. That corpus is more valuable than another 100 synthetic tests.
